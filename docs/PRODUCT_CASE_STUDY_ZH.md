# AI 穿搭推荐助手：从规则 MVP 到可控多模态推荐

## 项目摘要

AI 穿搭推荐助手是一个面向中文用户的 Streamlit 求职作品集项目。它从一个完全确定性的商品组合 MVP 开始，逐步加入图片上传、千问视觉理解、用户确认、图片偏好排序、自有单品补全和本地可视化商品卡片。

项目刻意没有让大模型直接生成商品：视觉模型负责回答“图片里是什么”，本地推荐器负责回答“在预算和尺码等条件下，CSV 中哪些商品可以组成搭配”。这种职责分离使结果可解释、可复现，也让没有配置 AI 服务的用户仍能使用普通推荐。

- 代码仓库：<https://github.com/ikuta46xie/outfit-recommender-mvp>
- 在线体验：仓库公开元数据未提供可核验的部署 URL，文档暂不放置未经确认的链接
- 当前验证：120 项自动化测试通过；本地编译、依赖一致性和 Streamlit 无头启动通过
- 数据范围：24 条明确标注的演示商品，不代表真实库存、价格或购买链接

## 背景

很多“AI 推荐”演示把自然语言生成直接当作推荐结果，但服装商品选择有强约束：用户买不起、穿不了、场景不合适或商品根本不存在时，再自然的推荐理由也没有价值。另一方面，图片中的颜色和风格又具有不确定性，不适合未经确认就成为硬条件。

本项目把这两类问题分开处理：

- 用规则保证商品存在、预算、尺码、场景、表单风格和排除颜色。
- 用视觉模型产出结构化候选信息，而不是商品决定。
- 用用户确认消除图片理解与业务枚举之间的最后一段歧义。
- 用有限、可测试的软加分改变合法候选顺序。

## 目标用户与使用场景

### 目标用户

- 希望快速得到可执行穿搭组合、但不想学习复杂搭配规则的用户。
- 已经有一件上衣、裤子或鞋子，希望补齐另外两个类别的用户。
- 有参考图片，希望推荐结果更接近某个主色或风格方向的用户。

### 典型任务

1. 通勤前按预算、尺码与风格生成三套候选。
2. 上传参考图，确认“黑色 + 商务”等偏好后重新排序。
3. 上传一件自有西装，确认它是上衣锚点，只购买裤子和鞋子。

普通推荐是基础能力；图片分析是可选增强，而不是系统可用性的前提。

## 核心问题

项目围绕四个产品与工程问题展开：

1. **如何保证结果来自商品库并满足用户约束？** 所有商品只从 CSV 读取，硬约束在候选生成前应用。
2. **如何使用不完全可靠的图片理解？** 视觉结果经过结构校验与用户确认，原始标签不直接进入推荐器。
3. **如何避免结果看似不同、实际反复复用同一商品？** 基础排序后增加确定性的贪心多样性重排。
4. **如何控制隐私与 API 成本？** 图片只在内存中处理，只有主动点击才调用，同图同模型在当前会话只分析一次。

## MVP 范围与边界

### 已包含

- 三种模式：普通推荐、参考图片偏好、围绕图片单品。
- 上衣、裤子、鞋子三类商品与最多三套结果。
- 本地 CSV 商品库和本地 SVG 商品示意图。
- 可选千问 `qwen3.7-flash` 图片理解。
- 严格结构化结果校验、用户确认、确定性软加分与规则理由。
- 会话级缓存、图片数量限制和友好错误分类。

### 明确不包含

- 虚拟试穿或真人穿着效果图生成。
- 图片识别品牌、价格、身份、年龄、性别或身材。
- 登录、数据库、跨会话用户画像。
- 真实电商库存、支付、购买链接或实时价格。
- 让大模型直接生成推荐商品或推荐理由。

## 用户流程

### 普通推荐

1. 选择场景、预算、上衣尺码、裤子尺码、风格和排除颜色。
2. 点击“生成穿搭”。
3. 查看最多三套上衣、裤子和鞋子卡片，以及总价和匹配分。

### 参考图片偏好

1. 上传图片；前端只预览，不自动分析。
2. 用户阅读隐私提示、勾选确认并主动点击“AI 分析服装”。
3. 系统在内存中修正 EXIF、限制最长边并压缩图片，再请求视觉模型。
4. 严格解析并校验 JSON；用户确认或修改参考主色与参考风格。
5. 选择“参考图片偏好”并生成穿搭。图片偏好只增加分数，硬约束不变。

### 围绕图片单品

1. 在同一份视觉分析结果下，用户确认名称、类别、主色与风格。
2. 自有单品以独立 `AnchorItem` 保存，与当前图片哈希及模型绑定。
3. 推荐器根据锚点类别，只从 CSV 选择缺少的两个类别。
4. 页面在锚点位置展示当前上传图片；采购总价只计算两个 CSV 商品。

确认偏好、确认锚点、修改表单和生成推荐都不会再次请求视觉模型。

## 关键产品决策

### 1. 不让模型生成商品

视觉模型不知道本地 CSV 的真实边界。让模型输出商品容易产生不存在的 ID、价格和库存，因此商品候选只由推荐器从 CSV 生成。

### 2. 不把 AI 原始标签直接用于排序

同一个服装可能同时被描述为“暗黑”“前卫”“正装”。业务侧只支持有限颜色和四类风格，直接传入会形成不可控映射。系统先用确定性规则预填，再让用户确认；用户修改永远优先。

### 3. 硬约束先于软偏好

预算、尺码、场景、表单风格和排除颜色决定候选是否合法。图片颜色、图片风格或锚点风格只给合法候选加分，不能挽救一个不合规组合。

### 4. 把普通模式作为降级路径

AI 服务未配置、鉴权失败、超时或额度不足都不应让整个产品失效。普通推荐没有外部调用，始终可运行。

### 5. 锚点不是商品

用户自己的衣服没有 CSV 商品 ID、价格和库存。把它伪造成 `Product` 会污染预算与来源校验，因此使用独立的不可变数据结构，页面也明确标注“不计入预算”。

### 6. 多样性是排序问题，不是新的硬过滤

前三套重复同一件商品会降低感知价值，但强制不重复可能在候选不足时少返回结果。贪心重排优先减少与已选结果重复的商品 ID；不足时允许复用，兼顾多样性与召回。

### 7. 演示图使用本地 SVG

远程商品图会引入授权、可用性和运行时网络依赖。脚本按 CSV 商品 ID 和颜色确定性生成不同服装轮廓，并通过安全映射限制路径访问。

## 技术方案与 AI 边界

### 推荐层

- `recommender.py`：加载 CSV，生成上衣 × 裤子 × 鞋子合法组合，计算基础分与可选图片偏好加分。
- `anchor_recommender.py`：根据锚点类别生成另外两个类别的笛卡尔积，计算采购总价、基础分和锚点加分。
- 两个推荐器都按分数、价格和商品 ID 确定性排序，再做贪心多样性重排。

### 视觉理解层

- `vision_analyzer.py`：拒绝损坏或明显过大的图片，修正 EXIF，将最长边限制在 1280 px，转 RGB 并压缩为 JPEG data URL。
- 通过 OpenAI Python SDK 调用阿里云百炼北京地域兼容接口，默认模型 `qwen3.7-flash`。
- 请求要求 JSON 对象、低温度、有限 Token、约 30 秒超时和最多 1 次重试。
- Python 对必需字段、列表上限、描述长度和 `confidence` 范围进行二次校验。

### 确认与状态层

- 图片哈希和模型组成 `cache_key`。
- 图片偏好与锚点确认结果都绑定当前 `cache_key`；上传新图片后旧确认不会误用。
- 会话缓存只保存结构化分析结果，不使用跨用户全局缓存。

AI 的输出到“结构化服装理解”为止。商品筛选、价格、排序、原因和图片卡片都不依赖生成式输出。

## 隐私、成本与安全

### 隐私

- 上传图与压缩图只在内存中存在，不写磁盘、数据库、日志或 GitHub。
- 锚点预览使用当前上传图片的内存字节；图片变化后不会展示旧预览。
- 页面在发送前展示明确提示并要求用户确认。

### 成本

- 不上传时零模型调用。
- 上传后仍需用户主动点击分析。
- 同图同模型在当前会话命中缓存，不重复调用。
- 每会话最多分析 3 张不同图片。
- 生成推荐和调整条件不调用模型。

### 安全

- Secrets 只从 `.streamlit/secrets.toml` 读取，仓库只提供占位示例。
- 不在用户界面或日志展示 Key、Workspace ID、Base URL、Base64 或完整上游异常。
- API 错误被归类为鉴权、超时、额度、网络、无效 JSON 或字段校验失败，再展示简洁消息。
- SVG 禁止脚本、外部资源、外部字体、`foreignObject`、Base64 图片和用户输入。
- 商品 ID 经过白名单格式校验，图片路径被限制在资产目录内，缺图回退到本地占位图。

## 当前验证

自动化测试总计 120 项，覆盖：

- 普通、图片偏好与锚点三种推荐路径的硬约束、来源、价格、分数、顺序和可复现性。
- 颜色/风格/类别映射、用户修改优先级、确认状态与新旧图片隔离。
- 图片缩放、EXIF、Base64、合法与非法 JSON、错误分类、模拟 API、缓存和会话限制。
- 推荐操作不新增 API 调用，以及测试环境不进行真实网络请求。
- 24 个 SVG 的存在、XML、安全、白色轮廓、占位图与路径穿越防护。
- 三列商品卡片、锚点内存预览和无远程图片依赖。

除 Pytest 外，项目还进行了 Python 编译、`pip check` 和 Streamlit 无头启动检查。仓库没有配置 GitHub Actions，因此当前结论仅代表本地验证，不等同于持续集成状态。

## 已知限制

- 商品和视觉资产均为演示数据，无法验证真实库存、成交或履约体验。
- 有限商品库可能让高约束组合无结果，或在候选不足时复用商品。
- 颜色协调和风格归一化是有限规则，不覆盖所有审美语境。
- 视觉模型对多人、多件混合、遮挡、低照度或非服装图片可能不确定。
- 没有用户账户、数据库、收藏、反馈闭环和跨会话个性化。
- 当前只评估排序与规则正确性，尚未进行真实用户可用性研究。

## 下一步：真实用户验证计划

下一阶段不会先堆叠更多模型，而是验证现有流程是否解决问题。计划：

1. 招募少量目标用户完成普通推荐、图片偏好和锚点补全三类任务。
2. 观察任务是否完成、卡点出现在哪一步，以及用户是否理解“硬约束”和“软偏好”。
3. 记录计划指标：任务完成率、首次可用推荐率、结果采纳意向、无结果率、图片分析失败率、用户修改 AI 预填的比例、单会话模型调用次数。
4. 用访谈验证用户更在意预算、颜色、风格还是单品补全，并据此决定下一轮优先级。
5. 若需要真实业务验证，再接入受控的商品源、库存和购买链接，同时补充可观测性与数据治理。

以上指标均是**未来计划收集的验证指标**，当前项目没有真实用户规模、转化率、收入或成本节省数据，也不对此作推断。
